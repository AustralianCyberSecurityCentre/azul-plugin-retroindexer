# Retroindexer-owned `azul-index` CLI

The `azul-index` CLI now belongs to **azul-plugin-retroindexer**, not
`azul-bedrock`. There are **no changes to Bedrock**; the CLI uses Bedrock's
existing `gosrc/store.FileStorage` implementations from the existing module
version in `go.mod`.

## Shared object-store protocol

Retroindexer's automatic publisher and `azul-index` write and read the same
immutable index keys:

```
retrohunt/indices/<sha256>.bgi
retrohunt/indices/<sha256>.ready
```

The marker contains the SHA-256 ID and is written only after the `.bgi` upload
succeeds. `list` returns only published IDs. `fetch` verifies the marker,
download length, and SHA-256 checksum before atomically exposing a local file.
The CLI serialises downloads to the same local output path using an advisory
file lock. BigGrep continues to read normal local `.bgi` paths.

**Breaking change for existing Retroindexer objects:** Earlier versions
published under `retrohunt/<processor>/bgi/<batch>-<sha256>.bgi` (or a custom
prefix followed by that label). Those objects do **not** have ready markers.
They are not visible to the new reader. Re-publish or migrate historical
indexes before switching Retrohunt over. Do not delete the old objects until
parity tests pass.

## Build

Run at the Retroindexer repository root:

```sh
go test ./internal/indexstorage ./internal/storage ./cmd/azul-index
go build -o bin/azul-index ./cmd/azul-index
```

The Dockerfile builds and installs **both**
`/usr/local/bin/azul-plugin-retroindexer` and `/usr/local/bin/azul-index`.
You can use a **pinned Retroindexer image** as the `INDEX_CLI_IMAGE` stage in
the search-only Retrohunt Dockerfile. For example, build Retrohunt with
`--build-arg INDEX_CLI_IMAGE=<registry>/azul-plugin-retroindexer:<pinned-tag>`.
The search-only Retrohunt image already expects an image containing
`/usr/local/bin/azul-index`. You must supply an image whose binary is
compatible with the target runtime architecture.

The CLI does *not* run a daemon; it is invoked as a short-lived process by
Retrohunt. Building it inside Retroindexer does not make the binary magically
available in Retrohunt's separate container.

## Retroindexer publisher settings

The existing background indexer continues using `RETROINDEXER_*` environment
variables. The relevant storage settings are:

```sh
RETROINDEXER_STORAGE_BACKEND=azure  # or s3
RETROINDEXER_STORAGE_BUCKET=retrohunt-indexes
RETROINDEXER_STORAGE_PREFIX=retrohunt/indices
RETROINDEXER_STORAGE_ENDPOINT=https://<account>.blob.core.windows.net/
RETROINDEXER_AZURE_ACCOUNT=<account>
RETROINDEXER_AZURE_ACCESS_KEY=<secret injected by Kubernetes>
```

For S3, use `RETROINDEXER_S3_REGION`, optional
`RETROINDEXER_S3_ACCESS_KEY`/`RETROINDEXER_S3_SECRET_KEY`, and
`RETROINDEXER_S3_SECURE`; IAM authentication is supported when keys are
absent. The normal indexing pipeline automatically calls the shared publisher
after indexing completed batches.

## CLI environment (used by Retrohunt)

For Azure Blob:

```sh
AZUL_INDEX_BACKEND=azure
AZUL_INDEX_AZURE_ENDPOINT=https://<account>.blob.core.windows.net/
AZUL_INDEX_AZURE_CONTAINER=retrohunt-indexes
AZUL_INDEX_AZURE_ACCOUNT=<account>
AZUL_INDEX_AZURE_KEY=<secret injected by Kubernetes>
AZUL_INDEX_PREFIX=retrohunt/indices
```

For S3 or compatible storage:

```sh
AZUL_INDEX_BACKEND=s3
AZUL_INDEX_S3_BUCKET=retrohunt-indexes
AZUL_INDEX_S3_ENDPOINT=http://<internal-s3-endpoint>:8333
AZUL_INDEX_S3_REGION=ap-southeast-2
AZUL_INDEX_S3_SECURE=false
AZUL_INDEX_S3_ACCESS_KEY=<access key>
AZUL_INDEX_S3_SECRET_KEY=<secret key>
AZUL_INDEX_PREFIX=retrohunt/indices
```

Leave `AZUL_INDEX_S3_ENDPOINT` empty to use the AWS SDK's configured default
endpoint. The default prefix is `retrohunt/indices` for **both** writer and
CLI. When customising it, `RETROINDEXER_STORAGE_PREFIX` and
`AZUL_INDEX_PREFIX` must be exactly the same and must contain at least a
source/label pair.

### Commands

```sh
azul-index put --file /tmp/test.bgi
azul-index list
azul-index fetch --id <64-char-sha256> --output /tmp/cache/test.bgi
```

`put` is optional for normal operations: Retroindexer automatically publishes
finished indexes using the same protocol.

## Test without any cloud dependency

```sh
export AZUL_INDEX_BACKEND=local
export AZUL_INDEX_LOCAL_ROOT="$(mktemp -d)"
printf 'index-fixture' > /tmp/example.bgi
id="$(azul-index put --file /tmp/example.bgi)"
azul-index list
azul-index fetch --id "$id" --output "/tmp/$id.bgi"
sha256sum "/tmp/$id.bgi"
```

This checks storage round trips, **not** whether the example bytes are a valid
BigGrep index. For production validation use a real `.bgi` generated by
`bgindex` and run the same query through BigGrep on the original and fetched
files.

## Operational notes

- The indexer still needs **local staging space** to build `.bgi` files. This
  is not a shared search PVC; its capacity and lifetime must be managed by
  Retroindexer's deployment.
- Retrohunt needs a separately configured **local ephemeral cache** for fetched
  indexes. Do not share a production PVC with the indexer.
- Cross-replica caches are independent. Size `emptyDir` and node ephemeral
  storage from actual index sizes and concurrent hunts.
- `fetch` currently scans a cached file to verify its SHA-256 on every call.
  This favours integrity over fastest possible repeated use; consider verified
  metadata caching later if it becomes a bottleneck.
- Index publication never erases old objects. Retention, pruning, and
  migration must be handled explicitly.
- Keep the complete index snapshot semantics: missing indexes should fail a
  hunt, not silently return an incomplete result.
- Provide credentials through Kubernetes Secrets or workload identity, never
  hardcode them in code or manifests.
